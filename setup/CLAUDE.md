# Memory (humona)
`humona` CLI = persistent memory (Obsidian vault, git-synced). Session start pulls + loads project card, working memory, recent episodes; session end consolidates + pushes. `humona help` for details. **Language: persist memory in English, reply to the user in the language they write in.** One consistent language keeps search, dedup and ranking working across sessions; the engine itself is language-agnostic (search folds diacritics and handles scripts written without spaces), so a user who wants notes in their own language says so in their own CLAUDE.md. Captured prompts stay verbatim — a record is not translated. Codebases: `<workspace>/projects/<area>/<repo>` (areas listed in `projects/README.md`; new one: `projects/new.sh <area> <name>`); project id = git remote name, independent of area.
1. Before exploring code: read `memory/projects/<p>/map.md`; use `humona outline`/`humona refs` instead of full-file reads (skill smart-explore). Recall progressively: `humona facts` (index of long-term notes) / `humona search "<topic>"` / `humona timeline` (one-liners) → `humona recall <path>` only for what's needed. A `<humona-recall>` block in a prompt is the memory system's own hint — treat it as a pointer, verify with `humona recall` before relying on it.
2. Durable learning → `humona remember -t semantic|episodic|procedural "Title" "body" [--kind decision|bugfix|gotcha|...] [--source PATH]`. One topic per note; a fact → semantic, something that happened on a date → episodic, a repeatable action → procedural. Scope it: `-p <project>` when it is about one project (that is what makes `humona whose` route a request there), `--global` only for lessons that apply everywhere. Link it from a related note (`[[name]]`) so it is not an orphan. On SIMILAR EXISTS: `--into PATH` / `--replace` / `--supersedes PATH` (old note was wrong/outdated) / skip.
3. Task start/change/milestone → `humona working -` (Goal, Current step, Open questions, Next; ≤30 lines). Every Next step carries its check: `<step> -> verify: <the check that proves it>` — a step with no check is not finishable by a fresh session.
4. After meaningful work → `humona episode "1-3 sentences: what, why, result — and how it was verified"`.
5. New project → after first exploration `humona card` + `humona map`; fill card + map Notes (`path:line — purpose`).
6. "Promotion candidates" in context → distill to long-term, then `humona promote`.
7. Never store secrets (user can wrap prompt text in `<private>…</private>`); sensitive/machine-specific → `--private`. ⚠ sync warning → `humona doctor --fix`.
8. Skip what code/git already records. Notes short, single-topic, `[[wikilinked]]`.
9. Multi-project work: `humona board` (kanban: in flight · blocked · next, per project), `humona task start|block|done --verify`, `humona whose "<request>"` when it is unclear which project a request belongs to. A `<humona-project-guess>` block means the prompt looks like another project — check its card before answering.
10. Wiki upkeep: `humona lint` (broken links, orphans, stale, duplicates, superseded-but-linked) → fix by linking, `--supersedes` or `humona archive`; decay and archiving never delete. Deleting is explicit and user-only: `humona forget <path|title>|--all|--older-than DAYS` (archived notes by default, `--anywhere` for live ones, needs `--yes` with no terminal) — only run it when the user asks to delete. `humona links <note>` for backlinks; `index.md` is generated (`humona index`, also at session end).

# Work (folded in from karpathy-guidelines, MIT — multica-ai/andrej-karpathy-skills)
11. Think first: state assumptions, name what is unclear instead of hiding it, and if several readings exist present them rather than silently picking one. If a simpler approach exists, say so.
12. Minimum code that solves the problem: no speculative features, no abstraction for single use, no configurability nobody asked for, no handling for impossible cases. 200 lines that could be 50 get rewritten.
13. Surgical edits: change only what the request needs, match the surrounding style, and mention adjacent dead code instead of deleting it — but do remove the orphans your own change created.
14. Every task becomes a verifiable goal ("add validation" → "write tests for invalid input, then make them pass"), and multi-step work states `step -> verify: check` before it starts. Weak criteria ("make it work") are the thing to fix first, not to work around.
